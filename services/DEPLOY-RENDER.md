# Deploying the Max platform on Render

Four services, defined in `services/render.yaml`. Everything runs in **Ohio**, the same AWS region as
the Neon database. The production database is already set up (see `services/README.md`).

| Service | Type | What it does |
| --- | --- | --- |
| `max-brain` | Private service (Docker) | The conversation brain. No public address: only the voice worker reaches it. |
| `max-voice-worker` | Web service (Docker) | Runs live calls. `POST /calls` needs `WORKER_TOKEN`. |
| `max-portal` | Web service (Docker) | The admin portal. |
| `max-maintain` | Cron job, hourly | Closes abandoned calls, deletes expired deals, enforces retention. |

The repository's root `render.yaml` (the old demo) is separate and is not touched.

## One-time setup

1. In https://dashboard.render.com, connect GitHub and give Render access to **jash2129/MAX.ZI**.
2. **New → Blueprint**, pick the repository, and set **Blueprint path** to `services/render.yaml`.
3. Render asks for each secret. Copy each value from the local file shown below; never paste them into
   chat, tickets or the repository. Every `.env*` file is git-ignored.

   | Service | Variable | Copy from |
   | --- | --- | --- |
   | max-brain | `DATABASE_URL` | `services/brain/.env.local` → `DATABASE_URL` (the brain's own login) |
   | max-brain | `XAI_API_KEY`, `GROK_MODEL`, `MAX_UNDERSTANDING`, `MAX_SPEECH` | optional; leave empty for approved lines word for word |
   | max-voice-worker | `DAILY_API_KEY` | your Daily dashboard → Developers |
   | max-voice-worker | `DEEPGRAM_API_KEY` | your Deepgram console |
   | max-voice-worker | `HEYGEN_API_KEY`, `HEYGEN_AVATAR_ID` | HeyGen (leave both empty for voice-only calls) |
   | max-portal | `PORTAL_DATABASE_URL`, `AUTH_DATABASE_URL`, `BETTER_AUTH_SECRET` | `services/portal/.env.prod` |
   | max-portal | `PORTAL_URL` | leave empty (Render's address is used) unless you use your own domain |
   | max-portal | `GOOGLE_*`, `MICROSOFT_*` | optional (sign-in with work accounts) |
   | max-maintain | `DATABASE_URL_UNPOOLED` | `services/control-plane/.env.local` → `DATABASE_URL_UNPOOLED` (the owner's connection) |

   `BRAIN_TOKEN` and `WORKER_TOKEN` are generated by Render. The worker receives the brain's token and
   its internal address automatically.
4. Click **Apply**. The first builds take several minutes (the voice worker's is the largest).

## Check it is working

1. **Portal:** open `https://max-portal-….onrender.com/sign-in`. You should see the sign-in page.
2. **First sign-in:** the platform owner's one-time link is in `services/control-plane/.env.owner-invite`.
   Replace its `http://localhost:3100` with the portal's address and open it. Set a password, then set
   up two-factor. The link lasts 7 days; make a new one with
   `npm run invite -- owner@example.com .env.owner-invite` in `services/control-plane`. To make the
   owner your own email first: `npm run owner-email -- <email>`.
3. **Voice worker:** open `https://max-voice-worker-….onrender.com/health`. Expected:
   `{"ok": true, "active_calls": 0, ...}`.
4. **A first call:** in `services/voice-worker`, with `WORKER_TOKEN` copied from the Render dashboard
   (max-voice-worker → Environment):

   ```bash
   WORKER_URL=https://max-voice-worker-….onrender.com WORKER_TOKEN=… .venv/Scripts/python scripts/start_call.py demo-mazda
   ```

   It opens the call in your browser. Afterwards it appears in the portal under Mazda Dealership → Calls,
   with its timings, review and dashboard figures.
5. **Maintenance:** max-maintain → **Trigger Run**. The log ends with a line like
   `{"abandoned":0,"deals_deleted":0,"turns_deleted":0,"recordings_deleted":0}`.

## Deploying a new version

Auto-deploy is off on purpose. A deploy restarts the brain and the worker, which ends calls in
progress. The brain finishes writing call records before it stops, up to 30 seconds.

1. Push to `main`.
2. When no calls are running (portal dashboard, or the worker's `/health` showing `active_calls: 0`),
   open each changed service and click **Manual Deploy → Deploy latest commit**. Deploy the brain
   before the worker when both changed.
3. Database changes: run `npm run migrate` in `services/control-plane` **before** deploying code that
   needs them. Take a Neon snapshot branch first.

## Cost (check Render's current pricing)

- `max-brain` and `max-portal`: Starter.
- `max-voice-worker`: Standard (2 GB of memory, for the speech models and up to 4 calls at once). This
  is the one to scale: add instances, or raise `MAX_CALLS_PER_WORKER` on a larger plan.
- `max-maintain`: billed only for the minutes it runs.
- Free instances are not suitable: they sleep, which ends calls and delays the first one.

## Known limits

- One brain instance keeps call state in memory. For several brain instances, set Upstash Redis
  (`UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`) on max-brain first.
- No customer-facing call page yet: calls are started with `scripts/start_call.py` (or anything else
  holding `WORKER_TOKEN`) and open in Daily's own call page, without Max's panels.
- Recordings are not stored yet.
